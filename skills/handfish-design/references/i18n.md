# Internationalization & Bidi (RTL)

Handfish provides **bidi readiness**, not a translation framework. That distinction is the whole mental model, so start here:

| Handfish provides | The app owns |
|-------------------|--------------|
| **Direction inheritance** in light DOM. Components inherit `dir` from `<html>`. | Set `dir` and `lang` from the user's locale. |
| **Overridable strings** through attributes or configuration options. | Supply translations, plurals, and localized number/date formatting (`Intl`). |
| **Logical CSS** in components and utility classes. | Use logical CSS so app layout also follows text direction. |
| **Bidi isolation** for the dynamic values it renders (`<bdi dir="auto">`) | Isolating dynamic values in **app** markup |

If you're looking for "how do I load Arabic strings" — that's app code (a dictionary, `Intl`, whatever framework). Handfish's job is to make sure that once your `<html>` is `dir="rtl"` with translated text, the components look and read correctly.

> **Before declaring that a component cannot be localized or does not exist, check `references/api-canonical.md`.** It lists all **21** custom elements and their actual attributes. Overrides exist for `select-dropdown` placeholders, `justify-button-group` tooltips, `AboutDialog` labels, and toast dismiss text. Use existing string overrides. Do not recreate a component that already exists.

## 1. Direction: set `dir` on `<html>`

There is one switch. Set `dir` (and `lang`) on the root element from the user's locale:

```html
<html lang="ar" dir="rtl" data-theme="dark">
```

or at runtime:

```js
document.documentElement.lang = 'ar'
document.documentElement.dir = 'rtl'   // flips the entire light-DOM tree
```

Because handfish uses **light DOM, not Shadow DOM**, the inherited CSS `direction` reaches *inside* every component — no `::part()`, no shadow-piercing. One attribute flips the menu bar, the dropdowns, the dialogs, and the inline content of every control at once.

`dir` is one of three orthogonal root-level axes — `data-theme` (color), `data-language` (typeface. See `theming.md` / `setup.md`), and `dir` (direction). Any combination is valid: `<html data-theme="neutral-dark" data-language="industrial" dir="rtl">` is fully supported.

## 2. Overridable built-in strings (per component)

These components provide English defaults and let the app override them. Set the attribute or configuration key to translated text.

| Component | String control | Default | Notes |
|-----------|----------------|---------|-------|
| `<select-dropdown>` | `placeholder` | `"Select..."` | Trigger text before selection |
| | `empty-text` | `"no options available"` | Shown when there are no options |
| | `dialog-title` | `"select"` | Option-picker dialog heading |
| | `dialog-label` | `"select option"` | Dialog `aria-label` |
| | `close-label` | `"close"` | Close-button `aria-label` |
| `<justify-button-group>` | `left-label` / `center-label` / `right-label` | `"Align left/center/right"` | Per-button `title` / accessible name (buttons are icon-only) |
| `<seance-dialog>` | `heading`, `copy`, `take-label`, `join-label`, `join-label-text`, `join-placeholder`, `copy-label`, `offline-label`, `offline-status-label`, `connecting-label`, `online-label`, `url-label` | (English) | Every label and status line is an attribute |
| `<session-status>` | `copy-label`, `offline-label` | (English) | |
| `<join-session-dialog>` | `title`, `copy`, `join-label`, `cancel-label` | (English) | |
| `<menu-bar>` | `bar-label` | `"Application menu"` | Bar's accessible name. Item labels come from your config |
| `AboutDialog` | `labels: { version, build, deployed, noisemakerEngine, local, unavailable }` | (English) | Constructor option. Merges over defaults |
| Toasts | `dismissLabel` (option) | `"Dismiss"` | `aria-label` on the toast close button |

The app directly supplies these strings, with no default to override:

- `<dropdown-menu>` `label` and `<dropdown-item>` text.
- `<select-dropdown>` `<option>` text.
- `<menu-bar>` configuration item labels.
- `AboutDialog` `name`, `tagline`, and `ecosystem`.
- All toast message text.

What handfish does **not** localize for you: numbers and dates. A `<slider-value>` or `<tempo-bar>` shows Western digits regardless of locale. If you need Arabic-Indic digits or localized dates, format them yourself with `Intl.NumberFormat` / `Intl.DateTimeFormat` and render them into your own label/`<output>`.

### Icons don't mirror

`<justify-button-group>` displays left, center, and right icons. Its `value` remains literal `left`/`center`/`right`. The icons do **not** mirror under RTL because alignment meanings do not change. Translate tooltips through `*-label`. Preserve the alignment semantics.

## 3. Logical CSS (so app layout flips too)

Handfish's own components already use logical properties. For your app CSS and any component overrides to flip alongside them, use logical properties too. Full table and rationale in `references/styling.md` → "Logical properties, not physical". The essentials:

- `margin-inline-start/end`, `padding-inline-start/end`, `inset-inline-start/end`, `border-inline-start/end`, `text-align: start/end` — all flip with direction.
- Flexbox/grid main-axis order already follows `direction` — a `display: flex` row starts at the inline-start on both sides.
- Utility classes: `.hf-border-inline-start`, `.hf-border-inline-end` (a token divider border that flips).

**Component alignment attributes:** `<dropdown-menu align>` accepts physical `left`/`right` **and logical `start`/`end`**. In an RTL-ready UI use `start`/`end` — they flip automatically, so you don't hand-flip `align` on locale change. (`<menu-bar>` is written with logical CSS throughout and needs no such attribute.)

## 4. Bidi isolation for dynamic values

A dynamic value may have a different direction from the surrounding UI. Examples include user names, session ids, git hashes, and file paths. Wrap these values in `<bdi dir="auto">` to isolate their direction:

```html
<span class="label">Version</span> <bdi dir="auto">1.2.0-rc.1</bdi>
```

`AboutDialog` already isolates and HTML-escapes its version, build hash, and deployment date. This keeps an English hash isolated inside an Arabic dialog. In app markup, wrap dynamic values beside translated text in `<bdi dir="auto">…</bdi>`. Set `unicode-bidi: isolate` on labels beside mixed-direction content.

## 5. Switching language at runtime

Attribute-driven strings update immediately. Changing `placeholder`, `label`, `bar-label`, `dialog-title`, or `*-label` updates the component. `<dropdown-menu>` and `<select-dropdown>` build internal lists from `<dropdown-item>` and `<option>` children at render time. Later changes to child `textContent` do not guarantee that the existing list renders again.

For language switching without a reload, rebuild the option/item lists after changing locale, or recreate the component. Changing child text alone is insufficient. Attribute labels and `dir` update without a rebuild.

## 6. Verification checklist (RTL)

Before declaring a UI localized:

- [ ] **Set `dir="rtl"` on `<html>`** and eyeball the page. Layout, alignment, borders, and inline flow should mirror. Anything stuck LTR is a physical CSS property that should be logical (check app CSS first. Handfish's own components should already flip).
- [ ] **Every built-in string is overridden.** Walk the table in §2 — no English `"Select..."`, `"Align left"`, `"Dismiss"`, `"Version"` leaking through in a non-English UI.
- [ ] **Dynamic values are isolated.** User-supplied strings and ids next to translated labels are wrapped in `<bdi dir="auto">`.
- [ ] **Numbers/dates are locale-formatted** where it matters (`Intl`), since handfish renders raw digits.
- [ ] **Theme sweep still passes.** RTL is orthogonal to theming — the same markup must work in `dark`, `light`, and RTL together. If something breaks only in RTL, it's a physical-property or isolation bug, not a token bug.
- [ ] **Runtime language switch re-renders list children** (§5), if the app switches locale without a reload.
